# Library author guide: shipping `purity.json` for PureAnalyzer

This guide is for **authors of F# (or .NET) libraries** who want consumers of **FSharp.PureAnalyzer** to treat their public APIs as pure leaves—**without** `[Pure]` attributes in source code.

**Consumers** only need PureAnalyzer (and optionally pure/impure decorations). They do not configure your purity data by hand.

**Model**

1. You generate a **`purity.json`** allowlist (same idea as the foundational set produced by `purity-collector`).
2. You **embed** it in your library DLL (and/or ship it next to the DLL in the NuGet package).
3. PureAnalyzer always loads its **built-in** foundational purity set, then **unions** every `purity.json` it finds on assemblies referenced by the project being analyzed.

> **Status:** Packaging and authoring conventions are defined here. Analyzer discovery of third-party `purity.json` is specified in [../strategy/purity-json-extension.md](../strategy/purity-json-extension.md) and lands in PureAnalyzer incrementally. Generate and pack today so packages are ready when discovery ships.

---

## 1. What you produce

### 1.1 Document format

Use the same schema as foundational / List A pure files (camelCase JSON):

```json
{
  "schemaVersion": "1.0",
  "packageId": "MyLib",
  "packageVersion": "1.2.3",
  "generatedAt": "2026-07-31T12:00:00+00:00",
  "generator": "purity-collector/0.x",
  "pureMethods": [
    {
      "fullName": "MyLib.MathModule.add",
      "origin": "automatic",
      "comment": ""
    }
  ]
}
```

| Field | Required | Notes |
|-------|----------|--------|
| `schemaVersion` | yes | Start with `"1.0"`. Unknown versions must be ignored by the analyzer. |
| `packageId` | yes | NuGet package id (or assembly identity for non-packaged builds). |
| `packageVersion` | yes | Version of **this** pure set (usually the package version). |
| `generatedAt` | yes | ISO-8601 timestamp. |
| `generator` | yes | Tool id/version string. |
| `pureMethods` | yes | Allowlist of pure **leaves** (public API surface recommended). |
| `pureMethods[].fullName` | yes | Stable full name (see naming notes below). |
| `pureMethods[].origin` | no | `"automatic"` or `"manual"` (collector default: automatic). |
| `pureMethods[].comment` | no | Free text for manual overrides. |

**Trust rule (enforced by PureAnalyzer):** only entries whose names belong to **your** assembly / package are applied. Claims about `System.*` or other packages are ignored.

### 1.2 Canonical file / resource name

| Placement | Name |
|-----------|------|
| Embedded resource in the library DLL | Logical name **`purity.json`** (preferred) |
| Sidecar next to the DLL (optional) | **`purity.json`** in the same directory as `MyLib.dll` |
| Repo / CI artifact before pack | e.g. `purity/purity.json` |

Do **not** invent random names. Discovery looks for:

1. Manifest resource ending with `purity.json` (case-insensitive), or exact logical name `purity.json`.
2. Sidecar file `purity.json` beside the assembly path.

## 2. Generate `purity.json` (no source annotations)

Use **purity-collector** (or a compatible tool) on the **built** library assembly—the same IL-oriented approach as foundational List A.

### 2.1 Local command

```bash
# Build your library first
dotnet build -c Release path/to/MyLib.fsproj

# Generate allowlist (public API only recommended for published packages)
dotnet run --project path/to/purity-collector -- \
  --defaults false \
  -a path/to/MyLib/bin/Release/net10.0/MyLib.dll \
  --package-id MyLib \
  --package-version 1.2.3 \
  --public-only true \
  -o purity/purity.json
```

When purity-collector is published as a global tool:

```bash
dotnet tool install -g purity-collector   # when available on nuget.org
purity-collector \
  --defaults false \
  -a path/to/MyLib.dll \
  --package-id MyLib \
  --package-version 1.2.3 \
  --public-only true \
  -o purity/purity.json
```

### 2.2 Naming of `fullName`

Prefer the same style purity-collector emits for BCL / FSharp.Core (namespace + type/module + member). PureAnalyzer normalizes FCS vs IL differences (`normalizeName`, generic arity, etc.). If a name never matches, that member simply will not be treated as a pure leaf.

## 3. Include `purity.json` in the library (required project snippets)

### 3.1 Embed in the DLL (recommended)

**F# (`.fsproj`):**

```xml
<ItemGroup>
  <!-- Generated by CI / purity-collector; commit or produce before pack -->
  <EmbeddedResource Include="purity\purity.json"
                    LogicalName="purity.json" />
</ItemGroup>
```

**C# (`.csproj`)** (if the library is C# with F# consumers):

```xml
<ItemGroup>
  <EmbeddedResource Include="purity\purity.json"
                    LogicalName="purity.json" />
</ItemGroup>
```

`LogicalName` must stay **`purity.json`** so discovery stays trivial.

### 3.2 Copy next to the DLL (monorepo / project references)

So project references find a sidecar even when tools look at `bin/`:

```xml
<ItemGroup>
  <None Include="purity\purity.json"
        CopyToOutputDirectory="PreserveNewest"
        CopyToPublishDirectory="PreserveNewest" />
</ItemGroup>
```

You can use **both** embed + copy.

### 3.3 Pack into NuGet (optional extra loose file)

Embedding is enough for discovery from the assembly. Optionally also pack a loose file for tooling:

```xml
<ItemGroup>
  <None Include="purity\purity.json"
        Pack="true"
        PackagePath="lib/$(TargetFramework)/"
        Visible="false" />
</ItemGroup>
```

(Adjust `PackagePath` so it sits next to your packaged DLL under `lib/...`.)

### 3.4 Full minimal library example

```xml
<!-- MyLib.fsproj (excerpt) -->
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <PackageId>MyLib</PackageId>
    <Version>1.2.3</Version>
    <IsPackable>true</IsPackable>
  </PropertyGroup>

  <ItemGroup>
    <Compile Include="Library.fs" />
  </ItemGroup>

  <ItemGroup>
    <EmbeddedResource Include="purity\purity.json"
                      LogicalName="purity.json" />
    <None Include="purity\purity.json"
          CopyToOutputDirectory="PreserveNewest" />
  </ItemGroup>
</Project>
```

Ensure `purity/purity.json` exists **before** `dotnet pack` (CI generates it, or commit the last released file).

## 4. GitHub Actions workflow (recommended)

Copy [templates/purity-json.yml](templates/purity-json.yml) into the library repo as `.github/workflows/purity-json.yml`, then set:

- project path  
- assembly output path after `dotnet build`  
- package id  

Typical flow:

1. Build Release.  
2. Run purity-collector → `purity/purity.json`.  
3. Commit (optional) or leave as pack input.  
4. `dotnet pack` / push NuGet (DLL embeds `purity.json`).

On every public API change, regenerate so the pure set does not go stale.

## 5. What consumers need

| Piece | Required? |
|-------|-----------|
| `FSharp.PureAnalyzer` (NuGet or Ionide analyzer drop) | Yes |
| Your library package | Yes |
| Extra settings for *your* purity.json | **No** |
| Your pure set for BCL | No (built into PureAnalyzer) |

Consumers still need the usual Ionide / decorations setup for badges; that is independent of third-party purity data. See [customer.md](../../customer.md).

---

## 6. Monorepo / in-solution libraries

Same convention:

1. CI or local script generates `purity/purity.json` for each library.  
2. Embed + `CopyToOutputDirectory`.  
3. App project references the library.  

PureAnalyzer, once discovery is implemented, loads `purity.json` from each referenced assembly path—not by “remembering” a previous analysis of another project.

---

## 7. Checklist for library authors

- [ ] Generate `purity/purity.json` with purity-collector (`--defaults false`, `--public-only true`).  
- [ ] Set `packageId` / `packageVersion` correctly.  
- [ ] Embed as `LogicalName=purity.json`.  
- [ ] Optionally copy to output for project references.  
- [ ] CI on main/tags regenerates before pack.  
- [ ] Do not list foreign assemblies’ methods in your pure set.  
- [ ] Smoke-test: consumer project calls a pure API; with PureAnalyzer enabled it can participate in pure call graphs (after analyzer support ships).
